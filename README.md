# ses-worklog

SES技術者が客先常駐先での業務内容を、**客先の固有名詞を落とした形で自社報告用に蓄積する**ためのローカル専用アプリケーション。

客先のGit・チケット・Wikiには契約上アクセスできないため、情報を自動取得する設計は取らない。
入力は「自分が自分の言葉で書いた走り書き」だけを前提とし、そこから機密を落として構造化・蓄積する。

## 現在の実装範囲（MVP）

```
入力（走り書き）
  ↓ ① 辞書による決定論的マスキング   … 実装済み・LLM 非依存
  ↓ ② ローカルLLM による文脈的抽象化 … 実装済み・LLM 未接続時は自動で縮退
  ↓ ③ 出力側での再マスキング         … 実装済み（最終ゲート）
  ↓ ④ 残存検査                       … 実装済み
蓄積（生ログは AES-256-GCM で暗号化して保存）
```

- 日次ログの入力・秘匿化プレビュー・保存・一覧・詳細
- 禁止用語辞書の CRUD、および辞書未登録の固有名詞候補の検出とワンクリック登録

### 週報の下書き生成

保守案件は同種の作業が繰り返されるため、入力は文章ではなく選択で完了させる。

```
定型作業（案件・作業種別をマスタから選択。種別は複数選択可）
  ↓ LLM 不使用
  ├→ 日別の作業内容テキスト（週報システムの作業内容欄へ）
  └→ 週次の件数集計（構造化データを数えるだけ。捏造の余地が無い）

非定型メモ（日次ログの自由記述）
  ↓ LLM
  └→ 【業務遂行】2 文目
```

未実装（次フェーズ）: 過去週報の CSV 取り込み、職務経歴の自動蓄積、スマホからのオフライン入力。

## 動かし方

前提: Java 17 以上。Maven は同梱の Wrapper が自動取得するため不要。

```
mvnw.cmd spring-boot:run
```

`http://localhost:8080` を開く。初回起動時に動作確認用のダミー用語が6件投入される。

### 暗号鍵

`src/main/resources/application-local.yml` に AES-256 の鍵が必要（生成済み・Git 管理外）。
鍵が無いとアプリは**起動しない**。生ログを平文で保存させないための意図的な設計。

鍵を再生成する場合:

```
powershell -Command "[Convert]::ToBase64String((1..32|%{Get-Random -Max 256}))"
```

**鍵を失うと保存済みの生ログは復号できなくなる。** マスキング済みの列は平文なので、
週報生成に必要なデータ自体は失われない。

## ローカルLLM

OpenAI 互換エンドポイント（Ollama / vLLM / LM Studio）であれば `base-url` の差し替えだけで動く。
未接続でも辞書マスキングだけで動作するため、LLM は必須ではない。

画面の状態表示は 4 状態を区別する。「到達できない」と「モデルが無い」は原因も対処も違うため。

| 表示 | 意味 |
|---|---|
| LLM 接続中 | 設定モデルが取得済みで利用可能 |
| LLM 未設定（モデル未取得） | サーバは動いているが設定モデルが無い |
| LLM 未接続（辞書マスキングのみ） | サーバに到達できない |
| LLM 無効（辞書マスキングのみ） | `worklog.llm.enabled=false` |

### 検証済みの構成

```
ollama pull qwen3.5:9b
```

6.6GB、VRAM 12GB に収まる。実測でパイプライン全体（辞書マスキング + LLM 抽象化 + 再マスキング）が
**700〜900ms** で完了する。

### reasoning_effort は必ず設定すること

思考型モデルは既定で思考モードが有効になっている。この状態では:

- 思考に 3839 トークンを消費し、本文が生成される前に文脈上限（4096）に達する
- `finish_reason=length` で `content` は空、所要時間は 90 秒

`reasoning-effort: none` を設定すると **90 秒 → 1 秒**になり、本文が正しく返る。

注意点として、思考内容は `<think>` タグではなく **`reasoning` という別フィールド**で返るため、
タグの除去では防げない。設定で抑制するしかない。
対応しないサーバでは `reasoning-effort` を空文字にすればフィールドごと送信しない。

### このマシンで動かせないモデル

Qwen3.8-Flash-Next（125B + N-gram埋め込み51B + MTP 4B）は 4bit 量子化でも約 90GB、
2bit でも約 45GB 必要で、VRAM 12GB + RAM 31GB では動かない。
MoE で活性パラメータが 6B なのは計算量が減るだけで、重み全体はメモリに載せる必要がある。

## 設計上の重要な決定

**1. 秘匿化の一次防衛線に LLM を使わない**

LLM に「固有名詞を隠して」と依頼する方式は取りこぼしが原理的に避けられない。
禁止用語辞書による決定論的な置換を必須の一次処理とし、LLM は「文脈的な言い換え」だけを担当する。
LLM が停止していても秘匿化の安全性は下がらない（品質だけが下がる）。

**2. 日本語のマッチングに正規表現の単語境界を使わない**

日本語には語境界が存在しないため `\b` が使えない。
辞書マッチングは Aho-Corasick（`org.ahocorasick`）で行い、
最長一致を優先することで「株式会社ABC」と「ABC」の競合時に壊れた出力にならないようにしている。

補助的な RiskScanner では正規表現を使うが、Java の `\b` は `Character.isLetterOrDigit` で
境界を判定するため漢字も単語構成文字とみなされる。
「伝票番号20260827001」のようなケースで検出漏れになるため、単語境界ではなく
前後の文字種を否定先読み/後読みで直接指定している。

**3. 週番号は独自規則。実データ 219 週で検証済み**

週報システムの「年月週」は ISO 週番号とも「月内の第 n 月曜」とも異なる。
月曜起点だが週が月をまたがず、第 1 週は月初日から、最終週は月末日で切り詰められる。
月末が週明けに落ちる月は第 6 週まで存在する（実データに 7 週分あった）。

過去 219 週分のエクスポートと突き合わせて全件一致を確認したうえで実装しており、
`ReportWeekTest` で境界を固定している。ここがずれると集計も生成も全て狂う。

**4. マスキング強度は宛先ごとに変える**

過去 4 年分を調べたところ、自社の週報システムには案件名もコンポーネント名も
そのまま書かれている一方、人名は出ていなかった。案件名まで伏せると
「どの案件の話か」が失われて週報として機能しない。

| プロファイル | 案件・システム・案件名 | 人名・その他 |
|---|---|---|
| INTERNAL（社内週報） | 残す | マスク |
| EXTERNAL（職務経歴・社外） | マスク | マスク |

既定は EXTERNAL とし、安全側に倒している。

**5. 【業務遂行】は 2 階建て。LLM が要るのは 2 文目だけ**

実データでは 1 文目が「依頼された業務を滞りなく遂行できている」旨の定型文で、
同一文が何週も連続する。2 文目だけがその週固有の非定型の貢献（手順書の整備など）。

1 文目は選択式にし、LLM は 2 文目にだけ使う。
該当する行動が日次メモに無ければ 2 文目は生成しない。人事評価に使われる欄なので、
書くことが無い週を埋めようとした瞬間に捏造が始まる。実データでも
【業務遂行】が空の週は 34 週あり、空欄で提出する運用実績がある。

**6. 生ログは暗号化して保持する**

破棄せず持つのは、辞書を改善したあとに過去ログを再処理できるようにするため。
DB 上は暗号文であることを `DailyLogPersistenceTest` で検証している。

## テスト

```
mvnw.cmd test
```

秘匿化の中核は決定論的処理なので、LLM 無し・インメモリDB で全て検証できる。

## セキュリティ上の注意

- **サーバは既定で `127.0.0.1` にのみバインドしている。** スマホから入力したい場合は
  `server.address` の変更が必要だが、生ログを保持するアプリを LAN に公開することになる。
  変更する場合は最低でも認証を追加すること（MVP には未実装）。
- **業務内容を自社報告に書ける範囲は、個別契約と NDA によって決まる。**
  本アプリは「書ける範囲の中で表現を整える」ためのものであり、
  書けないものを書けるようにするものではない。

## 次のステップ

1. 過去週報の CSV 取り込み → few-shot 例として文体の踏襲精度を上げる
   - エクスポートは CP932 のため `▶`『▷』が `?` に化け、HTML エンティティが
     二重エスケープされている。取り込み時に復元が必要
2. 案件終了時の職務経歴エントリ自動生成 → スキルシート更新の材料
3. PostgreSQL への移行（`compose.yaml` と `application-postgres.yml` は用意済み）
   - ベクトル検索は日次ログが年 250 件程度のため不要。総当たりで足りる

## 既知の制約

- `spring.jpa.hibernate.ddl-auto=update` を使用。列の削除やデータ移行は行われないため、
  スキーマ変更時は `WorkEntryTaskTypeMigration` のような移行処理を個別に書いている。
  Flyway を導入した時点で移行スクリプトへ置き換える。
- 禁止用語・案件・作業種別・定型文の編集は削除や無効化で代替する（更新機能は未実装）。
- 週報システムへの書き込みは行わない。生成物をコピーして貼り付ける運用とする
  （「提出」の誤操作を構造的に防ぐため、および社内システムとの結合を持たないため）。
- 認証機構なし。単一利用者のローカル実行のみを想定。
- `spring-boot:run` は JVM をフォークするため、Maven を止めてもアプリが残る場合がある。
  H2 のファイルロックが解放されず再起動に失敗したら、残存 java プロセスを終了させること。
